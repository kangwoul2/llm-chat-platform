## 1. 프로젝트 핵심

LLM API의 주요 병목은 서버 내부 계산보다 **외부 LLM 응답을 기다리는 I/O 시간**입니다.

```text
동시 요청 증가
  ↓
외부 LLM 대기 증가
  ↓
처리 중 요청 수 증가
  ↓
429 / 제한시간 초과 / 긴 꼬리 지연시간 증가
  ↓
무제한 동시 호출을 허용할 수 없음
  ↓
세마포어 / 대기열 / 재시도 / 과부하 제어 필요
```

따라서 이 프로젝트는 두 문제를 분리해서 다룹니다.

```text
서비스 안정성
- 비동기 I/O
- HTTP 연결 풀
- 세마포어
- 크기가 제한된 대기열
- 재시도 / 제한시간
- 멱등성
- 폴링 / SSE / WebSocket
- 관찰 지표

RAG 응답 품질
- 문서 등록
- 관련 문서 검색
- 검색 점수 기준
- 근거 부족 시 응답 차단
- 출처 반환
```

프로젝트와 면접에서는 **문제 → 원인 → 대안 → 선택 → 단점 → 검증** 순서로 설명합니다.

## 2. 왜 비동기 처리를 사용했는가

현재 작업의 주된 병목은 외부 LLM 응답 대기입니다.

```text
요청 해석
  ↓
네트워크 전송
  ↓
외부 LLM 응답 대기
  ↓
응답 해석
```

CPU 연산을 병렬화하는 것보다, I/O를 기다리는 동안 이벤트 루프가 다른 요청을 처리할 수 있도록 비동기 구조를 사용하는 것이 적합하다고 판단했습니다.

중요한 점은 **비동기 처리가 LLM 한 번의 응답시간을 줄여주는 것은 아니라는 점**입니다. 비동기 처리의 목적은 같은 시간 동안 더 많은 I/O 대기 요청을 효율적으로 관리하는 것입니다.

---

## 3. 왜 세마포어가 필요한가

비동기 API는 많은 요청을 동시에 시작하기 쉽습니다.

```text
100개 요청
  ↓
FastAPI
  ↓
제한 없이 100개 LLM 호출
  ↓
외부 LLM
  ↓
429 / 제한시간 초과 / 과부하
```

그래서 `asyncio.Semaphore`로 **외부 LLM에 동시에 보내는 호출 수**를 제한합니다.

```text
서버가 받은 동시 요청 수 ≠ 외부 LLM 동시 호출 수
```

면접에서는 다음처럼 설명합니다.

> 비동기 처리는 요청을 많이 받을 수 있게 해주지만, 그 요청을 그대로 외부 API에 동시에 보내면 오히려 과부하를 만들 수 있습니다. 그래서 세마포어로 외부 LLM 동시 호출 수를 별도로 제한했습니다.

---

## 4. 세마포어와 대기열의 차이

짧은 요청에서 필요한 것이 단순한 동시 호출 수 제한이라면 세마포어만으로 충분할 수 있습니다.

하지만 다음 요구가 생기면 대기열이 필요합니다.

- 현재 몇 건이 기다리는지 확인
- 대기시간 측정
- 요청 취소
- 서버가 감당할 수 있는 대기 건수 제한
- 처리 중 작업과 대기 작업 분리

그래서 긴 작업에는 **크기가 제한된 대기열 + 작업 처리자 + 요청 ID** 구조를 사용합니다.

```text
요청
  ↓
요청 ID 발급
  ↓
대기열
  ↓
작업 처리자
  ↓
완료 상태 저장
```

대기열이 가득 차면 메모리를 계속 늘리는 대신 HTTP 429로 요청을 거절합니다.

대기열의 목적은 응답시간 단축이 아니라 **과부하 상황을 통제 가능한 상태로 만드는 것**입니다.

## 5. RAG에서 근거 없는 응답을 어떻게 막았는가

검색 결과가 부족한데도 LLM을 호출하면 자연스럽지만 근거 없는 답변이 만들어질 수 있습니다.

```text
질문
  ↓
문서 검색
  ↓
검색 결과 부족
  ↓
LLM 호출
  ↓
그럴듯하지만 근거 없는 답변
```

이를 막기 위해 BM25 검색 결과의 최고 점수가 기준보다 낮으면 LLM을 호출하지 않습니다.

```text
질문
  ↓
BM25 검색
  ↓
최고 점수 >= 기준값 ?
  ├─ 예 → 검색 문서를 근거로 LLM 호출
  └─ 아니오 → 근거 부족 응답
```

현재 기본 기준값은 `0.55`입니다.

## 6. 전체 구조

![시스템 구조](docs/assets/system_architecture.svg)

```text
사용자
  ↓
FastAPI
  ↓
요청 ID / 관찰 지표
  ├─ 일반 비동기 대화
  │    ↓
  │  세마포어
  │    ↓
  │  공유 HTTP 연결 풀
  │    ↓
  │   LLM
  │
  ├─ 문서 기반 대화
  │    ↓
  │  BM25 검색
  │    ↓
  │  점수 기준 확인
  │    ↓
  │  근거 문서만 사용한 LLM 호출
  │
  └─ 긴 작업
       ↓
     제한된 대기열
       ↓
     작업 처리자
       ↓
  폴링 / SSE / WebSocket
```

| 구성 요소 | 역할 |
|---|---|
| FastAPI | HTTP 요청과 응답 처리 |
| 요청 추적 미들웨어 | 요청 ID 발급, 요청 지표 기록 |
| 공유 `AsyncClient` | HTTP 연결 재사용 |
| 세마포어 | 외부 LLM 동시 호출 수 제한 |
| 제한된 대기열 | 대기 작업 수와 과부하 관리 |
| 작업 처리자 | 대기열의 작업 실제 처리 |
| 문서 저장소 | 문서 저장과 검색 |
| RAG 서비스 | 검색 → 점수 확인 → 근거 기반 생성 |
| PostgreSQL | 대화/메시지 영속화 확장 지점 |
| Redis | 여러 서버 간 상태 공유와 분산 조정 확장 지점 |
| Kafka | 분석·평가 이벤트 분리 확장 지점 |

## 7. 주요 구현

### 7.1 동기 방식 기준 실험

```http
POST /api/v1/chat/sync-baseline
```

동기 방식과 비동기 방식의 차이를 실험하기 위한 기준 경로입니다. 동기 방식이 무조건 나쁘다고 가정하지 않고, 같은 조건에서 비교하기 위한 용도로 둡니다.

### 7.2 비동기 대화

```http
POST /api/v1/chat/async
```

```text
HTTP 요청
  ↓
멱등성 키 확인
  ↓
세마포어 획득
  ↓
비동기 LLM 호출
  ↓
결과 저장
  ↓
HTTP 응답
```

### 7.3 HTTP 연결 재사용

프로세스가 실행되는 동안 하나의 `httpx.AsyncClient`를 재사용합니다.

```text
요청마다 새 클라이언트 생성
→ TCP/TLS 연결을 반복 생성할 수 있음
→ 연결 설정 비용 증가

공유 클라이언트
→ Keep-Alive 연결 재사용
→ 연결 풀 사용
```

연결 풀의 크기도 무조건 크게 잡지 않습니다. 외부 LLM 동시 호출 제한과 함께 결정해야 합니다.

### 7.4 재시도

재시도 대상:

- 제한시간 초과
- 네트워크 오류
- HTTP 429
- HTTP 5xx

재시도하지 않는 오류:

- 400 잘못된 요청
- 401 인증 오류
- 입력값 검증 오류

재시도 간격은 지수적으로 늘리고 작은 무작위 지연을 더합니다. 무제한 재시도는 장애 상황에서 요청을 더 늘릴 수 있으므로 최대 횟수를 제한합니다.

### 7.5 제한된 대기열과 과부하 제어

```http
POST /api/v1/jobs
```

대기열이 가득 차면 요청을 더 받지 않고 HTTP 429를 반환합니다.

```text
대기열 가득 참
  ↓
추가 요청 거절
  ↓
HTTP 429
```

## 8. 폴링, SSE, WebSocket 비교

### 폴링

클라이언트가 일정 간격으로 상태를 다시 조회합니다.

장점:
- 구현이 단순함
- 연결이 끊겨도 다음 요청으로 복구 가능

단점:
- 완료되지 않은 상태에서도 반복 요청 발생
- 조회 주기만큼 결과 확인이 늦어질 수 있음

### SSE

서버가 하나의 연결을 유지하면서 클라이언트에 단방향으로 상태나 토큰을 전달합니다.

LLM 토큰 전송처럼 **서버 → 클라이언트 단방향 통신**에는 SSE가 비교적 단순한 선택입니다.

### WebSocket

양방향 실시간 통신이 필요한 경우 사용합니다.

단점은 연결 상태 관리와 서버 확장 시 운영 복잡도가 더 높다는 점입니다.

따라서 단순 토큰·상태 전송은 SSE를 먼저 검토하고, 양방향 실시간 메시지가 필요한 경우 WebSocket을 선택합니다.

## 11. 성능 검증 방법

성능 개선은 다음 순서로만 비교합니다.

```text
기준 상태 고정
  ↓
가설 작성
  ↓
한 가지 변수만 변경
  ↓
같은 부하로 재실행
  ↓
원본 결과 저장
  ↓
p50 / p95 / p99 / 처리량 / 오류율 비교
  ↓
단점까지 해석
```

주요 지표:

| 지표 | 확인 목적 |
|---|---|
| 처리량(RPS) | 단위 시간 처리 건수 |
| p50 지연시간 | 일반적인 요청의 체감 시간 |
| p95 / p99 | 느린 요청과 시스템 포화 확인 |
| 오류율 | 처리량 증가가 실패 증가로 만들어진 것인지 확인 |
| 처리 중 LLM 호출 수 | 외부 LLM에 가해지는 압력 확인 |
| 대기시간 | 과부하가 대기열로 이동했는지 확인 |
| 실제 처리시간 | 작업 처리 자체에 걸린 시간 |
| 알림 지연시간 | 작업 완료 후 클라이언트가 인지하기까지 걸린 시간 |

실험 항목:

```text
동기 기준 방식 vs 비동기 방식
무제한 동시 호출 vs 세마포어 제한
요청별 HTTP 연결 vs 연결 풀 재사용
직접 처리 vs 제한된 대기열
폴링 vs SSE vs WebSocket
검색 점수 기준에 따른 근거 부족 응답
```

측정하지 않은 수치는 성능 개선으로 적지 않습니다.

## 12. 멱등성과 경쟁 상태

현재 메모리 기반 멱등성 저장소는 같은 키로 완료된 결과를 다시 사용할 수 있습니다.

하지만 다음 경쟁 상태는 남아 있습니다.

```text
요청 A: 키 조회 → 없음
요청 B: 키 조회 → 없음
요청 A: 처리
요청 B: 처리
요청 A: 결과 저장
요청 B: 결과 저장
```

즉 `조회 → 처리 → 저장` 전체가 하나의 원자적 연산은 아닙니다.

여러 서버로 확장할 경우 다음 대안을 비교할 수 있습니다.

- DB 유일성 제약조건
- Redis `SET NX`
- 처리 중 작업 공유
- 멱등성 기록 테이블

분산 락부터 적용하기보다 더 작은 원자적 연산이나 DB 제약조건으로 해결할 수 있는지 먼저 확인합니다.

## 13. Redis와 Kafka의 역할 구분

### Redis

- 여러 서버가 작업 상태를 공유할 때
- 요청 제한 상태를 공유할 때
- 여러 서버 간 분산 조정이 필요할 때

### Kafka

- 하나의 완료 이벤트를 여러 소비자가 독립적으로 처리할 때
- 분석·평가·감사 처리를 사용자 API와 분리할 때
- 다시 읽을 수 있는 이벤트 기록이 필요할 때

```text
Redis → 공유 상태와 분산 조정
Kafka → 이벤트 기록, 재처리, 소비자 분리
```

Kafka를 분산 락처럼 사용하지 않습니다.

## 14. DB 트랜잭션 경계

LLM 네트워크 호출 전체를 DB 트랜잭션 안에서 기다리지 않습니다.

```text
좋지 않은 방식
BEGIN
  ↓
LLM 호출 3~20초
  ↓
DB 갱신
COMMIT

선택한 방향
짧은 DB 작업
  ↓
외부 LLM I/O
  ↓
짧은 DB 작업
```

외부 I/O 때문에 트랜잭션과 DB 연결을 오래 점유하지 않도록 트랜잭션 범위를 짧게 유지합니다.

## 18. 현재 한계

1. 작업 상태 저장소가 프로세스 메모리 기반이어서 재시작 시 상태가 사라집니다.
2. 메모리 기반 멱등성 처리는 동시에 들어온 같은 요청을 완전히 원자적으로 차단하지 못합니다.
3. BM25 문서 저장소는 단일 프로세스 실험용이며 대규모 벡터 검색 구조는 아닙니다.
4. SSE/WebSocket 상태 전달 내부에는 단순 폴링이 일부 포함되어 있습니다.
5. PostgreSQL 모델은 준비되어 있지만 모든 API가 DB 영속화와 연결된 것은 아닙니다.
6. Redis/Kafka 연동은 역할 비교를 위한 확장 지점이며 모든 요청이 사용하지는 않습니다.
7. 실제 LLM 제공자의 요청 제한과 토큰 스트리밍 특성은 별도 측정이 필요합니다.

## 19. 면접 답변 요약

> 외부 LLM 호출은 CPU 연산보다 I/O 대기가 긴 작업이라 비동기 처리를 적용했습니다. 다만 비동기로 요청을 많이 받을 수 있게 되면 외부 LLM에 호출이 한꺼번에 몰릴 수 있어서 세마포어로 동시 호출 수를 제한했습니다. 긴 작업은 제한된 대기열과 작업 처리자로 분리해 과부하를 제어했고, 요청 ID를 이용해 폴링·SSE·WebSocket으로 상태를 전달했습니다. RAG에서는 검색 근거가 부족한데도 답변하는 문제를 막기 위해 BM25 검색 점수 기준을 두었습니다. 성능은 처리량뿐 아니라 p95/p99 지연시간, 오류율, 대기시간을 함께 측정하도록 구성했습니다.

### 자주 나오는 질문

- 비동기 처리가 한 요청의 응답시간도 줄여주는가?
- 세마포어와 대기열은 어떤 차이가 있는가?
- 대기열이 왜 성능 최적화가 아니라 과부하 제어인가?
- HTTP 연결 풀을 너무 크게 잡으면 어떤 문제가 생기는가?
- 429 재시도에서 지수 백오프와 무작위 지연이 왜 필요한가?
- 폴링, SSE, WebSocket 중 어떤 기준으로 선택하는가?
- RAG 검색 점수 기준을 왜 두는가?
- 멱등성과 분산 락은 어떤 문제를 각각 해결하는가?
- PostgreSQL, Redis, Kafka의 역할은 어떻게 다른가?
- 평균 지연시간보다 p95/p99를 보는 이유는 무엇인가?

세부 내용은 [`docs/10_interview_questions.md`](docs/10_interview_questions.md)에 정리합니다.
