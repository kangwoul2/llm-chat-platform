# 면접 질문 정리

모든 답변은 **문제 → 원인 → 선택 → 단점 → 검증** 순서로 설명합니다.

## 왜 비동기 처리를 선택했나요?
LLM 호출은 CPU 연산보다 외부 응답을 기다리는 I/O 시간이 깁니다. 그래서 대기 중 이벤트 루프가 다른 요청을 처리할 수 있도록 비동기 구조를 사용했습니다. 목적은 한 번의 LLM 호출 자체를 빠르게 만드는 것이 아니라, 같은 시간 동안 더 많은 I/O 대기 요청을 효율적으로 관리하는 것입니다.

## 비동기 처리로 만들면 무조건 빨라지나요?
아닙니다. CPU 연산이 많은 작업에는 효과가 작고, 동기식 라이브러리가 이벤트 루프를 막고 있으면 오히려 병목이 생길 수 있습니다. 먼저 작업이 CPU 중심인지 I/O 대기 중심인지 확인해야 합니다.

## 세마포어와 대기열의 차이는 무엇인가요?
세마포어는 동시에 실행할 수 있는 작업 수를 제한합니다. 대기열은 기다리는 작업의 순서와 상태까지 관리합니다. 짧은 요청에서 단순 동시 호출 제한만 필요하면 세마포어가 더 작고, 긴 작업에서 대기 건수·대기시간·거절 정책까지 관리해야 하면 대기열이 적합합니다.

## 왜 WebSocket보다 SSE를 먼저 검토했나요?
LLM 토큰이나 작업 상태는 대부분 서버에서 클라이언트로 보내는 단방향 흐름입니다. 이 경우 양방향 통신이 가능한 WebSocket보다 SSE가 구조와 운영이 단순합니다. 사용자 입력을 실시간으로 다시 보내야 하거나 양방향 이벤트가 많아지면 WebSocket을 선택할 수 있습니다.

## HTTP 연결 풀이 왜 필요한가요?
같은 외부 서비스에 반복 요청할 때 TCP/TLS 연결을 매번 새로 만들지 않고 Keep-Alive 연결을 재사용할 수 있습니다. 다만 연결 풀을 너무 크게 잡으면 외부 서비스에 과도한 연결을 만들 수 있으므로 외부 LLM 동시 호출 제한과 함께 결정해야 합니다.

## Redis 분산 락과 Kafka는 어떤 차이가 있나요?
Redis 분산 락은 여러 서버가 같은 공유 자원을 동시에 수정하지 않도록 조정할 때 사용합니다. Kafka는 이벤트를 저장하고 전달해 생산자와 소비자를 분리하는 용도입니다. Kafka를 사용한다고 경쟁 상태가 자동으로 해결되는 것은 아닙니다.

## 왜 처음부터 마이크로서비스로 나누지 않았나요?
서비스를 분리하면 네트워크 실패, 배포, 관찰, 데이터 정합성 같은 운영 복잡성이 늘어납니다. 먼저 하나의 서비스 안에서 병목과 변경 경계를 확인하고, 독립 확장이나 장애 격리가 실제로 필요한 부분만 분리하는 것이 적절하다고 판단했습니다.

## 성능 개선을 어떻게 검증하나요?
같은 환경과 같은 부하에서 변경 전후를 비교합니다. 처리량, p95/p99 지연시간, 오류율, 대기시간을 함께 보고 원본 결과를 저장합니다. 평균 지연시간 하나만 보고 개선됐다고 판단하지 않습니다.

## 면접 30초 답변

> 외부 LLM 호출은 I/O 대기가 긴 작업이라 비동기 처리를 적용했습니다. 다만 비동기로 요청을 많이 받을 수 있게 되면 외부 LLM에 호출이 한꺼번에 몰릴 수 있어 세마포어로 동시 호출 수를 제한했습니다. 긴 작업은 제한된 대기열로 분리해 과부하를 제어했고, RAG에서는 검색 근거가 부족한 경우 LLM 호출을 막았습니다. 성능은 처리량뿐 아니라 p95/p99 지연시간, 오류율, 대기시간을 함께 측정하는 방식으로 검증합니다.
