# 문제 정의

## 프로젝트 한 줄 정의

**LLM API를 사용하는 백엔드에서 I/O 대기, 동시 요청 증가, 긴 작업, 결과 전달 방식이 시스템에 어떤 영향을 주는지 직접 구현하고 비교하는 프로젝트**입니다.

## 왜 이 프로젝트를 만들었는가

일반적인 LLM 데모는 `요청 → LLM → 응답`까지만 구현합니다. 실제 서비스에서는 다음 문제가 추가됩니다.

1. 외부 LLM 응답을 기다리는 시간이 길어 서버 자원을 효율적으로 사용해야 합니다.
2. 비동기로 전환해도 외부 LLM에 요청을 무제한으로 보내면 429, 제한시간 초과, 연결 포화가 발생할 수 있습니다.
3. 긴 작업은 HTTP 연결을 완료까지 유지하기보다 비동기 작업으로 분리할 수 있습니다.
4. 작업 결과를 폴링, SSE, WebSocket 중 어떤 방식으로 전달할지에 따라 요청 수와 결과 전달 지연시간이 달라집니다.
5. 여러 서버로 확장하면 메모리 대기열, 메모리 기반 멱등성, 프로세스 내부 락만으로는 전체 상태를 보호할 수 없습니다.
6. Redis 분산 락과 Kafka는 서로 역할이 다르며 실제 문제가 있을 때 선택해야 합니다.

## 핵심 질문

- 동기 방식과 비동기 방식은 동시 사용자가 늘어날 때 처리량과 p95 지연시간이 어떻게 달라지는가?
- 외부 LLM 동시 호출 수는 어느 정도로 제한해야 하는가?
- HTTP 연결 재사용은 반복 연결 생성 비용을 얼마나 줄이는가?
- 대기열을 사용했을 때 안정성과 대기시간 사이에 어떤 단점이 생기는가?
- 폴링, SSE, WebSocket은 결과 전달 방식에서 어떤 차이가 있는가?
- 멱등성은 재시도로 생기는 중복 요청을 어디까지 막아야 하는가?
- 프로세스 내부 락, DB 락, Redis 분산 락은 각각 어떤 범위를 보호하는가?
- Kafka는 락이 아니라면 어떤 문제를 해결하는가?

면접에서는 각 질문을 **문제 → 원인 → 선택 → 단점 → 검증** 순서로 답합니다.
